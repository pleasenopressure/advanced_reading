这里的**“基于主键的原子更新”**可以拆成三个词理解：

```text
主键 + 更新 + 原子
```

文档想表达的是：

> 向量库根据一条记录唯一的主键找到旧实体，并通过一次 `upsert` 操作，把这个实体替换成新内容；应用不需要自己先删除、再插入。

---

## 1. 什么是主键

主键 Primary Key 是一条记录的唯一身份。

假设向量库里保存的是 Chunk：

```json
{
  "chunk_id": "chunk-001",
  "doc_id": "refund-policy",
  "content": "退款将在 7 个工作日内完成",
  "embedding": [0.12, -0.31, 0.56],
  "version_id": 1
}
```

这里可以把：

```text
chunk_id = chunk-001
```

设为主键。

向量库中不能同时有两条主键都为 `chunk-001` 的记录，就像数据库中的身份证号不能重复。

---

## 2. 什么是 upsert

`upsert` 是两个单词的组合：

```text
update + insert
```

规则是：

```text
主键已经存在 → 更新原记录
主键不存在   → 插入新记录
```

伪代码可以理解为：

```python
if primary_key_exists(chunk_id):
    update_record()
else:
    insert_record()
```

但真正执行时不是让应用先查再决定，而是直接交给数据库：

```python
vector_db.upsert({
    "chunk_id": "chunk-001",
    "content": "退款将在 3 个工作日内完成",
    "embedding": new_embedding,
    "version_id": 2
})
```

# 3. 举一个完整例子

旧记录：

```json
{
  "chunk_id": "chunk-001",
  "doc_id": "refund-policy",
  "content": "退款将在 7 个工作日内完成",
  "embedding": [0.10, 0.25, -0.31],
  "version_id": 1
}
```

现在原文改成：

```text
退款将在 3 个工作日内完成。
```

重新生成向量后，执行：

```python
client.upsert(
    collection_name="knowledge_chunks",
    data=[{
        "chunk_id": "chunk-001",
        "doc_id": "refund-policy",
        "content": "退款将在 3 个工作日内完成",
        "embedding": [0.18, 0.41, -0.22],
        "version_id": 2
    }]
)
```

因为 `chunk-001` 已经存在，所以它不会新增第二条同主键记录，而是覆盖原实体。

更新后，逻辑上只剩：

```json
{
  "chunk_id": "chunk-001",
  "doc_id": "refund-policy",
  "content": "退款将在 3 个工作日内完成",
  "embedding": [0.18, 0.41, -0.22],
  "version_id": 2
}
```

不是：

```text
chunk-001 旧版：7 个工作日
chunk-001 新版：3 个工作日
```

而是同一个 `chunk-001` 变成了新版。

# 4. “原子”是什么意思

原子操作 Atomic Operation 的核心含义是：

> 对外看，这个操作是一个不可分割的整体，要么完成，要么不完成，不应该暴露执行到一半的中间状态。

不用 upsert 时，应用可能自己执行两步：

```text
第一步：删除旧记录
第二步：插入新记录
```

例如：

```python
vector_db.delete("chunk-001")
vector_db.insert(new_chunk)
```

这存在两个风险。

## 风险一：两步之间出现空窗

```text
删除旧记录成功
        ↓
新记录还没有插入
```

此时用户查询可能完全找不到这个 Chunk。

## 风险二：删除成功，插入失败

```text
删除旧记录：成功
插入新记录：失败
```

最终新旧内容都没有了。

而 upsert 从调用方角度是一次操作：

```python
vector_db.upsert(new_chunk)
```

应用不需要自行管理“先删后插”的中间状态。

可以简单理解为：

```text
手动 delete + insert：

旧记录 → 暂时不存在 → 新记录
              ↑
          可能出问题

upsert：

旧记录 ─────────→ 新记录
```

不过要注意，文档中的“原子更新”是工程层面的简化说法。不同向量数据库对并发可见性、失败回滚和一致性的具体保证可能不同，不能自动等同于关系数据库里完整的 ACID 事务。

# 5. 为什么说“只能覆盖同一主键实体”

这是这句话最重要的后半部分。

假设原文被切成三个 Chunk：

```text
旧版本：

chunk-001：退款申请条件
chunk-002：退款周期为 7 个工作日
chunk-003：退款到账方式
```

更新文档并重新切分后，只剩两个 Chunk：

```text
新版本：

chunk-001：退款申请条件及到账方式
chunk-002：退款周期为 3 个工作日
```

现在执行：

```text
upsert chunk-001
upsert chunk-002
```

结果是：

```text
chunk-001 → 被覆盖为新内容
chunk-002 → 被覆盖为新内容
chunk-003 → 没有人处理，仍然残留
```

因为 upsert 只知道你提交给它的主键：

```text
chunk-001
chunk-002
```

它不知道：

```text
chunk-003 已经不属于新版本了
```

最终向量库中可能变成：

```text
chunk-001：新版
chunk-002：新版
chunk-003：旧版残留
```

这就是文档说的：

> 如果重新切分后 Chunk 数量或者 `chunk_id` 发生变化，仍然需要按 `doc_id + version_id` 清理旧版本残留。

# 7. 原子更新的范围到底有多大

需要特别注意：这里的原子性通常只是**单个主键实体级别**的。

例如：

```text
upsert chunk-001
```

只能保证 `chunk-001` 这一条记录被更新。

它不自动保证下面这些操作作为一个整体成功：

```text
更新 chunk-001
更新 chunk-002
删除 chunk-003
更新 PostgreSQL
更新 Elasticsearch
```

可能出现：

```text
chunk-001：成功
chunk-002：成功
chunk-003 删除：失败
全文索引：失败
```

因此，不能把单条 upsert 理解为：

> 整篇文档在向量库、元数据库、全文索引中的所有数据都被事务性更新了。

它解决的是：

```text
一条旧记录如何安全地替换成一条新记录
```

而不是：

```text
整篇文档如何跨多个 Chunk、多个数据库保持一致
```

# 8. 两种常见的主键设计

## 设计一：稳定 Chunk ID

```text
chunk_id = doc-A-chunk-1
```

版本更新时主键不变：

```text
v1：doc-A-chunk-1
v2：doc-A-chunk-1
```

优点是可以直接 upsert 覆盖。

缺点是重新切分后，Chunk 的位置和语义可能已经改变，旧 Chunk ID 与新 Chunk 未必还能自然对应。

---

## 设计二：版本化 Chunk ID

```text
chunk_id = doc-A-v2-chunk-1
```

每个版本使用不同主键。

优点是：

- 保留历史版本；
    
- 容易审计和回滚；
    
- 不会意外覆盖旧数据。
    

缺点是：

- upsert 新版本实际上属于插入；
    
- 必须显式让旧版本失效；
    
- 查询必须过滤当前版本或 `is_deleted = false`。
    

生产中经常采用：

```text
doc_id       表示文档身份
version_id   表示版本
chunk_id     表示版本内的 Chunk
is_deleted   表示是否仍可检索
```

# 9. 一个比较安全的更新流程

```text
1. 根据 doc_id 找到当前旧版本
2. 解析并切分新文档
3. 为新 Chunk 生成向量
4. upsert 可以复用主键的 Chunk
5. 插入新增的 Chunk
6. 删除或软删除旧版本多余 Chunk
7. 更新元数据库中的当前 version_id
8. 更新全文索引
9. 全部完成后标记 index_status = ready
```

伪代码：

```python
old_chunk_ids = get_old_chunk_ids(doc_id)
new_chunks = parse_and_chunk(new_document)

new_chunk_ids = set()

for chunk in new_chunks:
    new_chunk_ids.add(chunk.chunk_id)
    vector_db.upsert(chunk)

stale_chunk_ids = old_chunk_ids - new_chunk_ids

for chunk_id in stale_chunk_ids:
    vector_db.delete(chunk_id)
```

关键在于这一句：

```python
stale_chunk_ids = old_chunk_ids - new_chunk_ids
```

它找出了旧版本中存在、但新版本中已经不存在的 Chunk。

# 10. 最终记忆方式

你可以把它压缩成：

```text
主键
= 一条 Chunk 记录的唯一身份证

upsert
= 有相同身份证就更新，没有就新增

原子更新
= 对这一条主键记录，以一次不可分割的操作完成替换

限制
= 只处理这个主键，不会自动清理其他旧 Chunk
```

所以这句话最准确的解释是：

> **Milvus 的 upsert 可以根据 `chunk_id` 覆盖同一个 Chunk 实体，避免应用自行执行“先删除、再插入”；但是它不知道整篇文档重新切分后哪些旧 Chunk 已经消失，因此仍需按 `doc_id` 和版本信息清理其他旧记录。**
