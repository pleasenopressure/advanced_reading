> 文档“新增了一段内容”，不一定等于“只新增几个完全独立的 Chunk”。如果系统重新执行原来的切分算法，原文档末尾的旧内容可能和新增内容重新组合成同一个 Chunk。

普通 RAG 更新文档时，系统通常会对整个文档或受影响章节重新执行同一套切分逻辑。末尾新增内容可能与原来的最后一个不完整 Chunk 合并，因此不一定只生成全新的 Chunk；系统需要通过 Chunk 内容哈希识别哪些旧 Chunk 实际发生了变化，再只对这些 Chunk 重新生成 Embedding。

## 1. 最常见的做法：重新切分整个文档

假设采用固定长度切分：

```
chunk_size = 100 tokens
overlap = 0
```

原文档有 950 个 Token：

```
chunk_1：token 1～100
...
chunk_9：token 801～900
chunk_10：token 901～950
```

注意，原来的最后一个 Chunk 只有 50 个 Token。

现在在文档末尾增加 80 个 Token，重新切分后会变成：

```
chunk_1～chunk_9：不变
chunk_10：原来的 50 Token + 新增内容前 50 Token
chunk_11：新增内容剩下的 30 Token
```

所以答案是：**会。**

原来的最后一个 Chunk：

```
旧 chunk_10 = 原文末尾 50 Token
```

会变成：

```
新 chunk_10 = 原文末尾 50 Token + 新增内容 50 Token
```

这时旧 `chunk_10` 的文本发生变化，其 `content_hash` 也会变化，因此需要重新生成 Embedding。

真正新增的并不只是 `chunk_11`：

```
需要重新 Embedding：
新 chunk_10
新 chunk_11
```

而原来的 `chunk_1～chunk_9` 可以继续复用。

---

## 2. 有 overlap 时，可能影响更多尾部 Chunk

假设：

```
chunk_size = 100
chunk_overlap = 20
```

每个 Chunk 向前重叠 20 个 Token：

```
chunk_1：1～100
chunk_2：81～180
chunk_3：161～260
...
```

在文档末尾追加内容时，最后一个不完整 Chunk 会扩展，并且可能产生新的重叠 Chunk。

因此受影响的通常是：

```
旧的最后一个 Chunk
+
新生成的一个或多个 Chunk
```

如果切分器对结尾边界有特殊合并逻辑，还可能影响倒数第二个 Chunk。

例如有些切分器不允许最后一个 Chunk 太短：

```
如果最后一个 Chunk < 30 tokens
就将它与前一个 Chunk 合并
```

追加内容后，这种合并关系可能改变，于是倒数两个 Chunk 都需要重新计算。

## 3. 为什么系统不能只把新增文本单独切分

假设旧文档结尾是：

```
退款审批完成后，款项通常会在
```

新增内容是：

```
三个工作日内退回原支付账户。
```

如果只把新增内容独立切分，会得到：

```
旧 Chunk：
退款审批完成后，款项通常会在

新 Chunk：
三个工作日内退回原支付账户。
```

两边的语义都不完整。

重新对文档末尾做切分，则可能得到：

```
退款审批完成后，款项通常会在三个工作日内退回原支付账户。
```

这显然是更合理的 Chunk。

所以普通 RAG 的增量更新通常不是简单地：

```
新增文本 → 单独切 Chunk
```

而是至少要重新处理新增位置附近的一段上下文。

# 4. “重新切分”不一定意味着重新 Embedding 全部 100 个 Chunk

需要区分两个动作：

```
重新切分文档
```

和：

```
重新生成全部向量
```

它们不是一回事。

系统可以这样做：

```
1. 使用同样的切分算法重新切分文档
2. 计算新版本每个 Chunk 的 content_hash
3. 与旧版本 Chunk 的 hash 比较
4. 相同的 Chunk 复用旧向量
5. 只对变化或新增的 Chunk 生成向量
6. 删除已经不存在的旧 Chunk
```

例如：

```
旧版本：
chunk_1 hash = A
chunk_2 hash = B
...
chunk_99 hash = Y
chunk_100 hash = Z

新版本：
chunk_1 hash = A
chunk_2 hash = B
...
chunk_99 hash = Y
chunk_100 hash = Z2
chunk_101 hash = N
```

则：

```
chunk_1～chunk_99：hash 不变，复用向量
chunk_100：hash 变化，重新 Embedding
chunk_101：新增，生成 Embedding
```

因此即使重新扫描并切分了整个文档，也不一定重新调用 Embedding 模型处理全部 Chunk。

重新切分主要消耗 CPU；Embedding 通常才是更昂贵的部分。

# 5. 如果是在文档中间插入，影响可能非常大

假设采用固定 500 Token 切分，并在文档开头插入 100 个 Token。

旧边界：

```
chunk_1：1～500
chunk_2：501～1000
chunk_3：1001～1500
```

插入后：

```
chunk_1：新内容 + 原 token 1～400
chunk_2：原 token 401～900
chunk_3：原 token 901～1400
```

虽然原内容大部分没变，但是所有后续 Chunk 的组合都移动了。

于是可能出现：

```
chunk_1 hash：变化
chunk_2 hash：变化
chunk_3 hash：变化
...
```

这叫做**切分边界漂移**。

所以：

- 末尾追加内容，通常只影响最后几个 Chunk；
- 文档中间插入内容，可能影响后面大量 Chunk；
- 文档开头插入内容，在朴素固定长度切分中可能导致几乎整个文档重算。

# 6. 不同切分策略的影响不同

## 固定 Token 数切分

```
每 500 Token 一个 Chunk
```

特点：

- 规则简单；
- 末尾追加通常只影响尾部；
- 中间插入容易导致后续边界整体漂移。

## 按段落或标题切分

例如：

```
第一章
  ├── 段落 1
  └── 段落 2

第二章
  ├── 段落 1
  └── 段落 2
```

如果只在第二章末尾增加一个段落，系统可以只重新处理第二章。

第一章完全不受影响。

这种结构化切分更有利于增量更新。

## 语义切分

根据主题变化决定边界。

新增内容可能改变附近的语义边界，因此受影响范围通常不是固定的，但一般仍集中在修改位置附近。

## Recursive Character Text Splitter

常见逻辑是依次尝试：

```
标题
→ 段落
→ 句子
→ 字符
```

它比单纯固定长度更稳定，但修改仍然可能改变受影响段落中的 Chunk 组合。

# 7. 生产系统如何降低边界漂移

更成熟的系统不会总是无脑地从文档第一个 Token 重新编号。

常见做法是以章节或结构节点作为更新单位：

```
doc
├── section_A
├── section_B
├── section_C
└── section_D
```

如果只修改 `section_C`：

```
section_A：不重新切分
section_B：不重新切分
section_C：重新解析、切分、Embedding
section_D：不重新切分
```

元数据中可以记录：

```
{
  "doc_id": "doc-001",
  "section_id": "section-C",
  "chunk_id": "section-C-chunk-03",
  "content_hash": "..."
}
```

这样更新范围从整篇文档缩小为一个章节。

还可以使用稳定锚点：

```
标题 ID
段落 ID
Markdown heading path
Confluence block ID
HTML DOM 节点 ID
```

而不是只使用：

```
第 1 个 Chunk
第 2 个 Chunk
第 3 个 Chunk
```

因为序号很容易随着插入内容整体移动。
