
| 存储形式      | 说明                   | 典型实现                       |
| --------- | -------------------- | -------------------------- |
| Token 级记忆 | 以自然语言或离散符号形式存储在外部数据库 | 向量库中的文本块、结构化 JSON          |
| 参数化记忆     | 将信息编码进模型参数中          | 预训练知识、LoRA 适配器、SFT 微调      |
| 潜在记忆      | 以隐式形式承载在模型内部表示中      | KV Cache、激活值、Hidden States |
这边深入的介绍一下这几个东西

# 什么是token级记忆
以自然语言或离散符号形式存储在外部数据库，它的优点是人可以直接打开查看，也容易修改和删除。
例如用户偏好，用token级记忆来进行存储就是：
```json
{
  "memory_type": "user_preference",
  "topic": "explanation_style",
  "example_first": true,
  "detail_level": "progressive"
}
```
可以看到这里的memory_type这些就是认为定义的离散符号。
另外各种信息在模型外的没有内化到模型参数本身进去的（例如数据库，以及各种document）这些都是token级记忆
这个记忆的使用方式基本是要先切分chunk然后保存，最后用于query来的时候进行检索（RAG的实现原理）
即：
用户表达偏好
    ↓
提取事实
    ↓
保存为文本或 JSON
    ↓
生成 Embedding（针对每一个文本块chunk都embedding到一个向量中）
    ↓
写入向量数据库
    ↓
未来根据问题检索
    ↓
把记忆重新放进 Prompt

# 什么是参数化记忆
这个则是将信息编码进模型参数中。
大模型本质上包含大量数学运算，而模型参数就是其中需要学习的数字。
例如一个极度简化的神经网络：
$$y = wx + b$$
这里的：
- $w$：权重
- $b$：偏置
就是模型参数。

参数化记忆与token级记忆不同的是，同一个问题（例如user A's perference), token级记忆会有一条明确的数据记录
```json
{
  "user": "A",
  "preferred_language": "Python"
}
```
但是参数化记忆，不是在模型中找到一个参数which can 直接对应pyhon
这个信息会分散在大量的参数中 which called 分布式表征。
类似于人学会骑自行车后，很难指出“骑自行车的记忆具体存在哪一个脑细胞中”
## 解析典型实现（预训练知识）
预训练其实就是给model喂大量的信息，然后让他在这个信息里预测下一个token，经过多轮训练后，模型参数里就形成了参数化的记忆 which 可以对应于语言规则，编程知识，世界知识这些东西。模型不需要每次都查询外部数据库，就可能直接回答。
但参数知识存在两个问题：
1. 可能过时。
2. 可能记得不准确。
## 解析典型实现（SFT微调）

SFT 全称是：

> **Supervised Fine-Tuning，监督式微调。**

它通常使用“输入—理想输出”样本继续训练模型。

例如我们希望模型学会一种代码审查方式，可以准备数据：

```
输入：
检查下面的 Python 代码。

理想输出：
1. 先说明代码目标；
2. 找出功能错误；
3. 分析时间复杂度；
4. 给出修改代码。
```

大量类似样本会让模型形成这种回答习惯。

微调前：

```
模型可能直接给修改后的代码。
```

微调后：

```
模型更可能先解释问题，再给代码。
```

此时，“回答时先解释再修改”被部分编码进了模型参数。
## 解析典型实现（LoRA 适配器）
LoRA 全称是：

> **Low-Rank Adaptation，低秩适配。**

完整微调需要修改模型大量原始参数，成本很高。

LoRA 的思路是：

> [[冻结原模型的大部分参数，只增加并训练一小部分额外参数]]。

可以把原模型比作一本已经印刷好的教材。

完整微调类似于：

```
重新修改并印刷整本教材。
```

LoRA 类似于：

```
不修改教材正文，而是增加一套专门的补充笔记。
```

运行时：

```
基础模型 + LoRA 适配器
```

共同决定输出。
### LoRA 示例

假设基础模型是通用编程助手。

我们使用公司代码训练一个 LoRA，让它学习：

- 使用 FastAPI
- 使用 Pydantic v2
- 不使用字段注入
- 测试使用 pytest
- 输出符合公司格式

那么：

```
通用模型 + 公司 LoRA
```

就会更符合公司习惯。

---

### 为什么 LoRA 也属于参数化记忆

因为 LoRA 最终保存的也是一组经过训练得到的数值参数。

它不是这样的可读记录：

```json
{
  "framework": "FastAPI"
}
```

而是一组矩阵：

```
Adapter weights:
[0.012, -0.087, 0.141, ...]
```

这些数字共同影响模型行为。
# 什么是潜在记忆
它是模型在处理某个 Token 时产生的内部向量。
例如输入：

```
Jack likes Python
```

每个 Token 都会在每一层 Transformer 中产生一个向量：

```
Jack   → [0.12, -0.43, 0.77, ...]
likes  → [0.36, 0.19, -0.28, ...]
Python → [0.81, -0.07, 0.52, ...]
```

这些数字不是简单的词典定义，而会综合表达：

- Token 的含义
- 所在位置
- 上下文
- 与其他 Token 的关系

例如单词：

```
bank
```

在下面两个句子中的 Hidden State 不一样：

```
I deposited money in the bank.
I sat on the river bank.
```

虽然 Token 都是 `bank`，但上下文不同，隐藏状态表达的语义也不同。
可以先记住一句话：

> **参数化记忆是模型长期“学会了什么”；潜在记忆是模型这一次运行时“正在想到什么”。**

模型内部可以抽象成：

$$h=f_\theta(x)$$
这里：

- $x$：输入 Token；
- $\theta$：模型参数；
- $h$：输入经过模型计算后得到的 Hidden States 或激活表示。
对应关系是：
```
θ：参数化记忆
x 经过 θ 计算得到的 h：潜在记忆
```
也就是说：
- **参数 $\theta$ 决定模型具备什么能力，它们长期存在于模型权重中；
- **隐藏状态$h$** 表示模型对当前输入的临时理解。
## 潜在记忆提供什么
在当前这一次运行中，模型会形成类似下面的临时内部表示：

```
当前人物：Mary
当前状态：没有发言
持续时间：三分钟
潜在动作：可能需要邀请 Mary
```

这些内容不是以普通文字保存，而是隐含在：

- Hidden States；
- 激活值；
- Attention 的 Key、Value；
- KV Cache。

当模型接下来生成：

```
Mary, what do you think about this?
```

它会利用这些临时内部表示。

但当当前推理结束、KV Cache 被清空时，这些表示通常也会消失。

这就是潜在记忆。
## 数学公式举例
假设模型中有一个权重矩阵：$$W_Q\in\mathbb R^{4096\times4096}$$它属于模型参数。

输入某句话后，模型计算：$$Q=XW_Q$$这里：

- $W_Q$：参数化记忆的一部分；
- $X$：当前输入的表示；
- $Q$：当前输入产生的激活值，属于潜在记忆。
模型还会计算：$$K=XW_K$$$$V=XW_V$$并将$K,V$ 存入 KV Cache。

所以：

```
WQ、WK、WV
    是长期保存的参数

Q、K、V
    是当前输入经过参数计算产生的临时结果
```

即使它们都是浮点数张量，它们的角色不同。

类比到一个计算公式：

$$y=wx$$

- w是长期学出来的参数；
- x 是当前输入；
- y 是当前计算结果。

不能因为 w 和 y 都是数字，就认为它们是同一种记忆。
## 解析典型实现（激活值）
激活值是神经网络在一次前向计算中，各个神经元产生的输出。

例如一个简化神经元：

$$z = wx + b$$

经过激活函数：

$$a = \operatorname{ReLU}(z)$$

这里的 $a$ 就是激活值。

在大模型中，激活值是一个很宽泛的概念，包括神经网络不同层产生的中间计算结果。

可以粗略理解为：

```
输入 Token
   ↓
Embedding
   ↓
第 1 层激活
   ↓
第 2 层激活
   ↓
第 3 层激活
   ↓
最终输出
```

Hidden State 通常也可以看作某种层级上的激活表示。

二者区别不必过度纠结：

- **Activation**：泛指网络中的中间输出。
- **Hidden State**：更强调某层对 Token 的内部表示。
## 解析典型实现（KV cache）
[[首先我会详细的解释一下KV cache机制设计出来的作用是什么，然后实现的理论基础。]]

KV Cache 是理解潜在记忆最关键的技术。

KV 分别代表：

- K：Key
- V：Value

它们来自 Transformer 的 Attention 机制。

### 1. 为什么需要 KV Cache

假设模型正在逐字生成：

```
The capital of France is Paris.
```

大模型通常是一个 Token 一个 Token 地生成：

```
The
The capital
The capital of
The capital of France
...
```

如果没有 KV Cache，每生成一个新 Token，模型都需要重新计算前面所有 Token 的 Attention 表示。

例如：

```
生成第 1001 个 Token 时，
重新计算前面 1000 个 Token。
```

这会非常浪费计算资源。

因此，模型把之前 Token 计算出的 Key 和 Value 保存起来：

```
过去 Token 的 K、V
        ↓
      KV Cache
```

生成下一个 Token 时，只需要计算新 Token 的 K 和 V，然后读取过去缓存。

---

### 2. KV Cache 如何承担“记忆”

假设对话是：

```
用户：我的机器人叫 Reachy。
用户：它现在没有连接实体硬件。
用户：我应该怎样测试它？
```

模型在处理后一句时，需要使用前面信息：

```
机器人叫 Reachy
当前没有实体硬件
```

之前 Token 对应的 Key 和 Value 已经在 KV Cache 中。

新 Token 可以通过 Attention 读取这些内容的内部表示，因此模型能够维持当前上下文。

所以 KV Cache 类似于：

> 模型在当前生成过程中的高速工作区。

---

### 3. KV Cache 和聊天记录的区别

聊天记录通常是可读文本：

```
[
  {"role": "user", "content": "我的机器人叫 Reachy"},
  {"role": "assistant", "content": "明白了"}
]
```

KV Cache 则是模型计算出的数值张量：

```
K: [batch, heads, sequence_length, head_dimension]
V: [batch, heads, sequence_length, head_dimension]
```

聊天记录可以长期存在数据库中。

KV Cache 通常：

- 存在 GPU 显存或内存里
- 体积较大
- 不能直接阅读
- 主要服务当前推理
- 会话结束后通常被清除

因此它更像 RAM 或 CPU Cache，而不是硬盘文件。
