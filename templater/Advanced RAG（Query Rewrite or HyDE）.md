# 一、Advanced RAG 中的术语

典型链路：

```
Query Rewrite / HyDE
→ 混合检索
→ Rerank
→ 上下文压缩
→ LLM 生成
```

## 1. Query Rewrite：查询改写

查询改写是把用户原始问题改写成一个**更适合检索的查询**。

用户说话往往比较口语化、简略，或者依赖前面的对话：

```
用户原问题：
这个怎么申请？
```

结合对话历史后，可以改写为：

```
改写后的查询：
英国学生签证 Graduate Route 应如何申请？
```

它可以做的事情包括：

- 补全省略的信息；
- 消除代词，例如“它”“这个”；
- 将口语改成文档中的正式术语；
- 拆分复杂问题；
- 增加同义词；
- 去掉与检索无关的内容。

例如：

```
原问题：
电脑坏了找谁？

改写：
公司笔记本电脑发生硬件故障时，应联系哪个部门报修？
```

### 主要解决的问题

用户的表达方式与知识库文档的表达方式不一致，导致检索不到。

但查询改写也有风险：LLM 可能错误理解用户意图，把问题改偏。

---

## 2. HyDE：假设性文档嵌入

HyDE 全称是：

> **Hypothetical Document Embeddings，假设性文档嵌入**

它不是直接把用户问题拿去检索，而是先让 LLM 为这个问题生成一段“假设答案”，然后用这段假设答案去检索真实文档。

流程是：

```
用户问题
→ LLM 生成一段假设答案
→ 将假设答案转换为 Embedding
→ 检索与假设答案相似的真实文档
```

例如用户问：

```
员工离职时如何归还公司设备？
```

LLM 先生成一段假设答案：

```
员工应在离职当天，将电脑、门禁卡和其他公司资产
交还给 IT 部门或直属管理人员。
```

然后系统不是用原问题检索，而是用这段完整的假设答案检索。

### 为什么可能更有效？

用户问题通常很短：

```
设备怎么还？
```

而知识库中的文档通常是陈述句：

```
离职员工应在最后工作日归还所有公司资产。
```

问题和答案在语言形式上差异较大。

HyDE 先生成一段“像文档一样的文本”，可以缩小查询与文档之间的表达差异。

### 要注意

HyDE 生成的假设答案不一定正确。

不过它的目的不是直接回答，而是：

> 利用假设答案中的语义和关键词，帮助找到真正的文档。

---

## Query Rewrite 和 HyDE 的区别

|方法|生成什么|用什么检索|
|---|---|---|
|Query Rewrite|一个更清楚的问题|改写后的问题|
|HyDE|一段假设性的答案或文档|假设答案的 Embedding|

例如原问题：

```
迟交怎么办？
```

Query Rewrite：

```
学生作业迟交两天会受到什么处罚？
```

HyDE：

```
作业迟交后，学校通常会按照迟交天数扣除一定比例的分数……
```

---

## 3. 混合检索：Hybrid Search

混合检索是同时使用多种检索方法，然后合并结果。

最常见的组合是：

```
关键词检索 BM25
+
向量语义检索
```

### 关键词检索擅长什么？

擅长精确匹配：

- 产品型号；
- 错误代码；
- 人名；
- 文件编号；
- 法律条文编号；
- 专业缩写。

例如：

```
Error E1047
RTX 5060
ISO 27001
合同编号 A-2026-031
```

这些查询使用关键词检索通常更可靠。

### 向量检索擅长什么？

擅长语义相似，即使没有使用完全相同的词也能命中。

例如：

```
Query：
怎么把买的东西退掉？

文档：
消费者可以通过订单页面发起退款申请。
```

两者关键词并不完全一致，但语义接近。

### 为什么要混合？

因为二者互补：

```
关键词检索：精确，但可能不理解同义表达
向量检索：理解语义，但可能漏掉编号和专有名词
```

混合检索会分别得到两组结果：

```
BM25 结果
向量检索结果
       ↓
分数融合或排序融合
       ↓
统一候选结果
```

---

## 4. Rerank：重排序或精排

Rerank 是对第一阶段找出的候选文档进行更准确的重新排序。

通常流程是：

```
初始检索快速召回 50 个 Chunk
              ↓
Reranker 逐个判断它们与问题的相关性
              ↓
保留最相关的 5 个 Chunk
```

第一阶段检索重点是：

> 尽量不要漏掉相关文档。

Rerank 阶段重点是：

> 从候选结果中选出真正最相关的文档。

### 为什么不一开始就用 Reranker 搜索整个知识库？

因为 Reranker 通常计算成本较高。

向量检索可以非常快地从百万个 Chunk 中找出几十个候选；Reranker 再对这几十个候选做精细判断。

类似于：

```
Retriever：海选
Reranker：精面
```

### 常见 Reranker

一种常见形式是 [[Cross-Encoder]]：

```
[用户问题, 文档 Chunk]
          ↓
     Reranker 模型
          ↓
      相关性分数
```

它同时阅读问题和文档，因此通常比单纯比较两个 Embedding 更准确，但速度更慢。

---

## 5. 上下文压缩：Context Compression

上下文压缩是从检索到的 Chunk 中，进一步删除与问题无关的内容，只保留真正有用的部分。

例如检索到了一个很长的 Chunk：

```
公司电脑由 IT 部门统一采购。
电脑通常每四年更新一次。
如果员工离职，应在最后工作日归还电脑和充电器。
设备损坏需要填写维修申请表。
```

用户的问题是：

```
离职时什么时候归还电脑？
```

压缩后可能只保留：

```
如果员工离职，应在最后工作日归还电脑和充电器。
```

### 主要作用

- 减少输入 Token；
- 降低 LLM 成本；
- 减少上下文噪声；
- 避免无关信息干扰模型；
- 允许放入更多真正相关的文档。

### 压缩不等于普通摘要

摘要通常是概括全文，而上下文压缩是：

> 围绕当前 Query，有针对性地保留相关句子。

同一个 Chunk 面对不同问题，压缩结果可能不同。

---

## 6. LLM 生成：Generation

这是最后一步。

系统将以下内容组织成 Prompt：

```
系统指令
+
用户问题
+
检索并处理后的证据
+
回答格式要求
+
引用要求
```

然后让 LLM 基于证据生成自然语言答案。

例如：

```
参考资料：
员工应在最后工作日归还电脑和充电器。

问题：
员工离职后什么时候归还电脑？

回答：
根据公司设备管理规定，员工应在最后工作日归还电脑和充电器。
```

LLM 在这里负责：

- 理解问题；
- 综合多个文档；
- 提取关键信息；
- 组织语言；
- 比较不同资料；
- 按要求添加引用。

它不是负责寻找全部知识，知识主要由前面的检索链路提供。
# 用一个例子串起 Advanced RAG

用户问：

> 我的电脑坏了，怎么搞？

系统可能这样处理：

### 1. Query Rewrite

```
公司员工使用的笔记本电脑发生硬件故障时，
应该通过什么流程申请维修？
```

### 2. HyDE，可选

生成假设答案：

```
员工应先联系 IT 服务台，并通过内部系统提交设备维修工单。
```

### 3. 混合检索

同时搜索：

```
向量检索：
寻找语义上与“电脑故障处理”相关的内容

BM25：
搜索“电脑”“硬件故障”“维修工单”“IT 服务台”
```

### 4. Rerank

从 30 个候选 Chunk 中选出最相关的 5 个。

### 5. 上下文压缩

只保留：

```
员工应通过 Service Portal 提交 Hardware Repair 工单。
紧急情况可以拨打 IT 服务台电话。
```

### 6. LLM 生成

```
你可以先通过公司的 Service Portal 提交 Hardware Repair 工单。
如果设备完全无法使用，可以同时联系 IT 服务台。
```
