## 1. 状态机的运行原理

有限状态机（FSM）可以理解成一张**状态转移图**。

它包含：

- 当前状态
    
- 输入字符或 token
    
- 转移规则
    
- 接受状态
    

运行时，从初始状态开始，每读取一个输入，就根据规则跳到下一个状态。

例如只允许识别 `HIGH`：

```text
q0 --H--> q1 --I--> q2 --G--> q3 --H--> q4
```

只有最终到达 `q4`，输入才合法。

如果读到：

```text
H → E
```

但 `q1` 没有接收 `E` 的转移，就立即判定非法。

在大模型生成中，状态机可以根据当前状态，屏蔽所有不能产生合法状态转移的 token。

## 2. CFG 和状态机的区别

|对比|有限状态机 FSM|上下文无关文法 CFG|
|---|---|---|
|表示形式|状态和状态转移|产生式规则|
|是否有额外记忆|没有，只有有限状态|通常通过栈维护递归结构|
|擅长|线性、固定格式、正则模式|嵌套、递归、层次结构|
|任意深度括号|不能|可以|
|实现复杂度|较简单|较复杂|

简单记忆：

> FSM 适合“一条固定路线”；CFG 适合“结构里面还可以继续包含同类结构”。

---

## 3. 分别适合什么场景

### FSM：订单号格式检查

要求订单号：

```text
以 O 开头，后面是 12～20 位数字
```

例如：

```text
O123456789012
```

状态机只需要记录：

```text
是否读到了 O
已经读了多少位数字
是否达到最少 12 位
是否超过 20 位
```

这类问题没有递归嵌套，FSM 很适合。

其他典型场景：

- 固定枚举：`LOW / MEDIUM / HIGH`
    
- 手机号、邮编、日期等格式
    
- 正则表达式匹配
    
- 简单协议流程
    

---

### CFG：嵌套 JSON

例如：

```json
{
  "user": {
    "orders": [
      {
        "items": [
          {
            "name": "coffee"
          }
        ]
      }
    ]
  }
}
```

对象里面可以有对象，数组里面又可以有对象，嵌套深度不固定。

CFG 可以通过递归规则描述：

```text
Value  → String | Number | Object | Array
Object → "{" Members "}"
Array  → "[" Values "]"
```

因为 `Object` 和 `Array` 内部又能包含 `Value`，所以可以继续递归。

其他典型场景：

- 任意深度括号匹配
    
- JSON、XML 的嵌套结构
    
- 编程语言语法
    
- 自然语言句法结构
    
- 递归的树形数据 Schema
    

## 总结

```text
固定格式、线性规则 → FSM
递归嵌套、层次结构 → CFG
```

在结构化输出中，FSM 适合约束局部字段格式，CFG 更适合约束整个嵌套 JSON 结构。
