# ANN 的通用两阶段结构

大部分 ANN 算法都可以抽象成两个阶段。

## 第一阶段：候选召回

使用索引快速找到一小批“可能相似”的向量：

```
100 万个向量
      ↓ ANN 索引粗筛
2000 个候选向量
```

## 第二阶段：精确距离计算

再对这 2000 个候选计算真实余弦距离、内积或欧氏距离：

```
2000 个候选
     ↓ 精确距离计算
返回 Top-10
```

因此，ANN 中的“近似”通常主要发生在：

> 候选集生成阶段。

它不一定意味着最终候选之间的距离也是随便估算的。很多系统在得到候选后，仍然会使用原始向量进行精确重排。

---

# 三、图导航是怎么实现的

典型代表是：

> HNSW。

图导航的核心想法是：

> 相似的向量之间提前建立连接，查询时沿着“越来越接近 Query”的方向移动。

---

## 1. 建索引时：把向量组织成近邻图

假设有一些二维向量：

```
A、B、C 在左侧
D、E、F 在中间
G、H、I 在右侧
```

HNSW 会让空间中相近的节点互相连接：

```
A —— B —— D —— E —— G
|   /      |   /      |
C          F          H —— I
```

每一个节点保存：

- 自己的向量；
- 自己连接的若干邻居节点 ID；
- 可能所在的图层。

例如：

```
{
  "node": "E",
  "neighbors": ["D", "F", "G", "H"]
}
```

这相当于提前保存了：

> “从 E 出发，哪些节点在语义空间中离 E 比较近？”

---

## 2. 查询时：只比较当前节点的邻居

假设查询向量 Q 靠近节点 I。

搜索从入口节点 A 开始：

```
当前节点：A
邻居：B、C
```

计算：

```
distance(Q, A)
distance(Q, B)
distance(Q, C)
```

发现 B 离 Q 更近，于是移动到 B。

然后检查 B 的邻居：

```
A、C、D
```

发现 D 更近，于是移动到 D：

```
A → B → D → E → G → H → I
```

它不会计算 Q 到图中所有节点的距离，只会计算路径附近节点的距离。

这就是图导航减少计算量的方式。

---

## 3. 为什么普通近邻图还不够

假设数据非常多，图中有 100 万个节点。

如果每次只能从一个局部邻居移动到另一个局部邻居，可能需要走很多步：

```
A → B → C → D → E → F → ...
```

所以 HNSW 增加了多层结构。

---

## 4. HNSW（Hierarchical Navigable Small World） 的分层结构

可以把它想成地图上的交通网络：

```
最高层：高速公路
中间层：城市主干道
底层：街区小路
```

对应图结构：

```
Layer 2：     A ---------------- G

Layer 1：     A ------ D ------- G ------ I

Layer 0：     A-B-C-D-E-F-G-H-I-J-K...
```

上层节点少、连接跨度大；底层节点多、搜索精细。

查询过程：

```
从最高层入口开始
        ↓
快速跨越很远距离
        ↓
找到大致区域
        ↓
下降一层
        ↓
继续细化
        ↓
到底层搜索局部候选
```

因此，HNSW 不是从 A 沿底层一步步走到 I，而可能是：

```
高层：A → G
中层：G → I
底层：搜索 I 周围节点
```

---

## 5. HNSW 为什么可能漏结果

图导航通常采用贪心策略：

> 当前看到哪个邻居更接近 Query，就优先往哪个方向走。

问题在于，图中可能存在局部最优：

```
               真正最近邻
                   X
                  /
入口 → A → B → C
              \
               D
```

查询走到 C 后，C 的所有直接邻居可能都比 C 更远，于是搜索停止。

但真正最近的 X 可能需要：

```
C → 一个暂时更远的节点 → X
```

才能到达。

如果算法只保留一条贪心路径，就可能错过 X。

因此 HNSW 实际不会只保留一个当前节点，而是维护一个候选队列。

---

## 6. `ef_search` 的具体作用

HNSW 查询时通常维护两个集合：

```
候选队列 candidates
当前最好结果 results
```

候选队列按照“距离 Query 的远近”排序。

每次：

1. 取出当前最有希望的节点；
2. 展开它的邻居；
3. 计算这些邻居到 Query 的距离；
4. 将有希望的邻居加入候选队列；
5. 持续搜索。

`ef_search` 控制的是：

> 查询过程中允许保留和探索多少个候选节点。

例如：

```
ef_search = 10
```

只保留较少候选，搜索很快，但可能走错路。

```
ef_search = 200
```

同时探索更多路径，更不容易陷入局部最优，但距离计算次数更多。

所以：

```
ef_search 小
→ 搜索路径少
→ 延迟低
→ 漏掉真正近邻的概率高

ef_search 大
→ 搜索路径多
→ 延迟高
→ 召回率更高
```

---

## 7. HNSW 实际减少了什么

暴力搜索：

```
计算 Query 与所有 100 万个节点的距离
```

HNSW：

```
计算 Query 与入口节点的距离
    ↓
计算若干邻居
    ↓
沿图导航并展开候选
    ↓
可能总共检查数百或数千个节点
```

例如：

```
暴力搜索：1,000,000 次向量距离计算
HNSW：2,000 次向量距离计算
```

具体数量取决于：

- `m`；
- `ef_construction`；
- `ef_search`；
- 数据分布；
- Top-K；
- 向量维度。
# 四、空间划分是怎么实现的IVF（**IVFFLAT**：**Inverted File with Flat storage/search**，通常也直接写作 **Inverted File Flat**）

典型代表是：

> IVF、IVFFLAT。

- **IVF**：**Inverted File Index**，中文常译为**倒排文件索引**。  
    它先用聚类把向量分进多个 `list/桶`，查询时只搜索距离 Query 最近的几个桶。
- **IVFFLAT**：**Inverted File with Flat storage/search**，通常也直接写作 **Inverted File Flat**。  
    其中：
    - `IVF`：先用聚类缩小搜索范围；
    - `FLAT`：桶内仍保存**未压缩的原始向量**，并对桶内候选逐个计算真实距离。

所以 IVFFLAT 的完整逻辑是：

```
全部向量
   ↓ 聚类成多个倒排桶（IVF）
选择离 Query 最近的几个桶
   ↓
在这些桶中对原始向量暴力计算距离（FLAT）
   ↓
返回 Top-K
```

它和 **IVF-PQ** 的区别是：

```
IVFFLAT：桶内保存原始向量，精度较高，占用空间较大
IVF-PQ：桶内保存量化压缩编码，内存更省，但会产生量化误差
```

因此这里的 `Flat` 不是说整个数据库都全表扫描，而是说：

> **只在 IVF 选中的少量桶内部，使用未压缩向量做 Flat 精确比较。**

它的核心思路是：

> 先把整个向量空间切分成多个区域，查询时只搜索离 Query 最近的几个区域。

---

## 1. 建索引时：对向量做聚类

假设有 100 万个向量。

使用 K-Means 将它们分成 1000 个簇。

每个簇有一个中心向量：

c1,c2,…,c1000c_1,c_2,\ldots,c_{1000}c1​,c2​,…,c1000​

每个原始向量会被分配给距离最近的中心：


例如：

```
Cluster 1：退款、退货、售后相关向量
Cluster 2：物流、快递、配送相关向量
Cluster 3：密码、登录、账户相关向量
...
```

真实的聚类并不认识“退款”“物流”这些文字，它只根据向量距离分组。

---

## 2. 建立倒排列表

每个聚类中心对应一个向量 ID 列表：

```
中心 C1
→ [向量 3、向量 18、向量 205、...]

中心 C2
→ [向量 7、向量 96、向量 102、...]

中心 C3
→ [向量 1、向量 23、向量 600、...]
```

这就是 IVF 中的 Inverted File，倒排列表。

它表达的是：

> 哪些原始向量属于这个空间区域。

---

## 3. 查询时：先比较聚类中心

查询向量 Q 到来后，不先和 100 万个原始向量比较，而是先和 1000 个聚类中心比较：

```
distance(Q, C1)
distance(Q, C2)
...
distance(Q, C1000)
```

假设最近的是：

```
C18、C35、C102
```

那么系统只读取这三个桶中的向量。

---

## 4. 在选中的桶中精确扫描

假设：

```
C18：1000 条向量
C35：900 条向量
C102：1100 条向量
```

系统只需对大约 3000 条向量计算精确距离：

```
100 万条
   ↓ 比较 1000 个中心
选择 3 个桶
   ↓
精确比较约 3000 条
```

而不是扫描全部 100 万条。

---

## 5. `lists` 和 `probes` 分别控制什么

### `lists`

表示建立多少个聚类桶。

例如：

```
lists = 1000
```

就是把数据大致分成 1000 个区域。

`lists` 越大：

- 每个桶更小；
- 区域划分更细；
- 查询时桶内扫描量下降；
- 但中心数量增加；
- 聚类和索引管理成本上升。

---

### `probes`

表示查询时检查多少个桶。

例如：

```
probes = 1
```

只搜索最近的一个桶，速度快，但容易漏结果。

```
probes = 20
```

搜索最近的 20 个桶，召回率更高，但扫描向量更多。

---

## 6. IVF 为什么会漏结果

假设 Query 位于两个聚类区域的边界：

```
      Cluster A      |      Cluster B
                     |
        Q            |   真正最近邻 X
                     |
```

虽然 Q 被判断为更接近 Cluster A 的中心，但它真正最近的向量 X 可能位于 Cluster B。

如果：

```
probes = 1
```

只搜索 Cluster A，就会漏掉 X。

如果：

```
probes = 2
```

同时搜索 A 和 B，就可能找到 X。

所以 IVF 的近似误差来源主要是：

> 只搜索部分聚类桶，而真正的近邻可能位于未被搜索的桶中。

# 五、量化是怎么实现的

典型代表是：

> PQ，也就是 Product Quantization，乘积量化。

量化解决的不只是“搜索多少向量”，还解决：

- 原始向量太占内存；
- 距离计算太慢；
- 内存带宽成为瓶颈。

它的核心思想是：

> 不再保存和计算完整的 float32 向量，而是用较短的离散编码近似表示向量。

---

# 六、为什么原始向量很占空间

假设每个向量：

- 1024 维；
- 每一维使用 float32；
- 每个 float32 占 4 字节。

单个向量大小：

1024×4=4096 bytes

约 4 KB。

1 亿个向量仅原始向量就约为：

4 KB×100,000,000≈400 GB

这还没有计算索引、元数据、数据库开销。

更重要的是，搜索时 CPU 需要不断从内存读取这些浮点数。很多时候真正的瓶颈不是加减乘除，而是：

> 内存无法足够快地把大量向量送给 CPU。

---

# 七、PQ 如何压缩一个向量

假设原始向量有 8 维：

x=[0.1,0.8,0.2,0.4,0.9,0.7,0.3,0.5]
为了方便说明，把它分成 4 个子向量，每个子向量 2 维：

```
子向量 1：[0.1, 0.8]
子向量 2：[0.2, 0.4]
子向量 3：[0.9, 0.7]
子向量 4：[0.3, 0.5]
```

真实系统可能把 1024 维向量分成 64 或 128 个子空间。

---

## 1. 为每个子空间训练码本

对第一个子空间的所有二维子向量做聚类，得到若干中心：

```
码本 1：

code 0 → [0.0, 0.9]
code 1 → [0.2, 0.7]
code 2 → [0.8, 0.1]
...
```

对第二、第三、第四个子空间也分别建立码本。

---

## 2. 用中心编号替代原始子向量

假设：

```
[0.1, 0.8] 最接近码本 1 的 code 0
[0.2, 0.4] 最接近码本 2 的 code 7
[0.9, 0.7] 最接近码本 3 的 code 3
[0.3, 0.5] 最接近码本 4 的 code 5
```

那么原始向量：

```
[0.1, 0.8, 0.2, 0.4, 0.9, 0.7, 0.3, 0.5]
```

可以近似保存为：

```
[0, 7, 3, 5]
```

这几个数字只是码本编号。

如果每个码本有 256 个中心，一个编号只需要 8 bit，也就是 1 字节。

原本每个子向量可能需要多个 float32，现在只需要一个字节编号。

---

# 八、查询时如何用 PQ 计算距离

假设查询向量也分成 4 个子向量：

```
q1、q2、q3、q4
```

系统提前计算查询子向量到每个码本中心的距离。

例如第一个子空间：

```
distance(q1, codebook1[0])
distance(q1, codebook1[1])
...
distance(q1, codebook1[255])
```

得到一个查找表：

```
table1[0] = 0.12
table1[1] = 0.35
table1[2] = 0.81
...
```

对其他子空间也建立类似表。

数据库中的某个压缩向量编码为：

```
[0, 7, 3, 5]
```

那么 Query 到这个向量的近似距离可以直接查表并相加：

$$\tilde d(q,x)
=
table_1[0]
+
table_2[7]
+
table_3[3]
+
table_4[5]$$

不需要读取和计算原始浮点向量。

查询过程变成：

```
读取几个短整数编码
       ↓
数组查表
       ↓
加法
```

而不是：

```
读取 1024 个 float32
       ↓
做 1024 次乘法/减法
       ↓
累加
```

因此速度和内存效率都会提高。

---

# 九、量化为什么会造成精度损失

因为一个真实子向量：

```
[0.13, 0.82]
```

可能被近似成聚类中心：

```
[0.10, 0.80]
```

另一个真实子向量：

```
[0.07, 0.76]
```

也可能被映射到同一个中心。

量化后，它们的细节差异消失了。

所以：

$$x\neq\hat x$$

其中：

- x：原始向量；
- x^\hat：量化重建出来的近似向量。

量化距离：

$$\tilde d(q,x)$$

并不完全等于真实距离：

$$d(q,x)$$

因此可能出现：

```
真实距离：
A 比 B 更接近 Query

量化距离：
B 看起来比 A 更接近 Query
```

---

# 十、IVF-PQ 是如何组合空间划分和量化的

IVF-PQ 一般使用两层筛选。

## 第一层：IVF 选择区域

```
100 万个或 1 亿个向量
       ↓
比较聚类中心
       ↓
选择少数几个桶
```

## 第二层：PQ 快速扫描桶内数据

桶内不保存或不完全依赖原始完整向量，而使用短编码：

```
桶内 PQ 编码
       ↓
查表计算近似距离
       ↓
获得候选 Top-N
```

可选的第三层：

## 第三层：使用原始向量重排

如果系统保存了原始向量，可以对最好的少量候选再计算真实距离：

```
PQ 找到 Top-100
       ↓
读取这 100 个原始向量
       ↓
精确距离计算
       ↓
返回最终 Top-10
```

这称为：

> Reranking 或 exact refinement。

于是完整过程是：

```
全量向量
   ↓ IVF 选择少数桶
桶内压缩向量
   ↓ PQ 近似距离快速筛选
少量候选
   ↓ 原始向量精确重排
最终 Top-K
```

# 十一、三种方法分别减少了什么

|方法|核心数据结构|减少计算的方式|
|---|---|---|
|图导航|近邻图|只沿有希望的邻居路径搜索|
|空间划分|聚类中心和倒排桶|只搜索与 Query 接近的区域|
|量化|码本和短编码|用近似编码代替完整浮点向量计算|

可以理解为：

## 图导航

解决：

> 在大量向量中，应该沿什么路径快速接近目标？

## 空间划分

解决：

> Query 大概属于哪个空间区域？

## 量化

解决：

> 即使仍需扫描很多候选，能否用更小、更快的表示计算距离？

---

# 十二、一个完整的实际例子

假设数据库中有：

```
1 亿个向量
每个向量 768 维
目标返回 Top-10
```

## 暴力搜索

```
Query
  ↓
读取 1 亿个完整向量
  ↓
计算 1 亿次真实距离
  ↓
返回 Top-10
```

---

## IVF-PQ 搜索

### 第一步：比较聚类中心

假设有 10000 个聚类中心：

```
Query 与 10000 个中心比较
```

### 第二步：选择 20 个桶

```
只扫描 20 个最接近的空间区域
```

假设这些桶总共包含 20 万个向量。

### 第三步：使用 PQ 编码计算近似距离

```
扫描 20 万个短编码
```

而不是读取 20 万个完整 float32 向量。

### 第四步：选出 Top-1000

```
20 万 → 1000 个候选
```

### 第五步：读取原始向量进行精确重排

```
1000 个候选
  ↓
真实距离
  ↓
最终 Top-10
```

最终完整距离计算从：

```
1 亿次
```

下降到：

```
1000 次
```

另外做了一些更便宜的：

- 聚类中心距离；
- PQ 查表；
- 候选排序。

# 十三、为什么 ANN 叫“近似最近邻”

近似主要可能来自三个地方。

## 1. 搜索路径不完整

HNSW 没有探索所有图路径，可能错过真正最近邻。

## 2. 搜索区域不完整

IVF 只检查部分桶，真正最近邻可能位于未搜索的桶。

## 3. 距离本身被近似

PQ 使用量化向量计算近似距离，排序可能和真实距离有偏差。

因此 ANN 不是说：

> 随机返回几个差不多的结果。

而是：

> 有意识地放弃穷尽式搜索，通过索引参数控制漏检概率。

---

# 十四、ANN 的参数本质上都在控制“搜索预算”

虽然不同算法参数名不同，但本质非常相似。

|算法|参数|实际含义|
|---|---|---|
|HNSW|`ef_search`|查询时探索多少图节点|
|IVF|`probes` / `nprobe`|查询时搜索多少个聚类桶|
|PQ|code size、子空间数|使用多少信息近似一个向量|
|LSH|hash tables、probes|检查多少个哈希桶|

参数调大通常意味着：

```
搜索更多候选
→ 更多距离计算
→ 延迟和资源消耗增加
→ 召回率提高
```

参数调小则相反。
ANN 的完整工程逻辑可以总结为：

```
索引阶段：
提前花时间和空间组织向量

查询阶段：
用索引快速缩小范围

精排阶段：
对少量候选计算更准确的距离

最终效果：
牺牲少量召回率，换取数量级的速度提升
```
