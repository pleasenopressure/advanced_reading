# 什么是向量数据库

向量数据库是：

> 专门存储、管理和检索高维向量的数据库系统。

例如：

- Milvus；
- Qdrant；
- Weaviate；
- Pinecone；
- Zilliz Cloud。

它除了保存向量，一般还负责：

- 向量索引；
- Top-K 相似度搜索；
- 元数据过滤；
- 数据新增、删除和更新；
- 持久化；
- 分区和分片；
- 多租户；
- 集群扩展；
- 备份和恢复。

## 向量数据库保存什么

它通常同时保存三类数据：

```
1. 向量
2. 向量对应的文本或对象 ID
3. 元数据
```

例如：

```json
{
  "id": "chunk_1001",
  "text": "用户可以在收到商品后七天内申请退款。",
  "metadata": {
    "document_id": "refund_policy.pdf",
    "category": "售后",
    "page": 3,
    "version": "2026-01",
    "tenant_id": "company_a"
  },
  "vector": [0.14, -0.52, 0.81, ...]
}
```
## 原始文本是什么

原始文本是这个 Chunk **实际包含的正文内容**，也是检索完成后最终提供给 LLM 阅读的内容。

例如：

```
用户可以在收到商品后七天内申请退款。
```

它主要有两个作用：

1. 返回给用户或 LLM，作为回答问题的知识依据；
2. 在入库时交给 Embedding 模型，生成向量。

流程是：

```
原始文本
   ↓ Embedding 模型
向量
   ↓ 检索命中后
原始文本被放入 LLM 上下文
```

所以向量只是原始文本的语义表示，不能完全代替原始文本。LLM 最终需要阅读的仍然是文字，而不是 `[0.14, -0.52, ...]` 这样的数字。

---

## 元数据是什么

元数据是：

> **用于描述这段原始文本的信息。**

它通常不是正文内容本身，而是告诉系统：

- 这段文本来自哪里；
- 属于哪个分类；
- 是哪个版本；
- 谁可以访问；
- 位于原文哪一页；
- 什么时候创建或更新。

例如原始文本是：

```
用户可以在收到商品后七天内申请退款。
```

描述它的元数据可以是：

```
{
  "source": "售后服务手册.pdf",
  "page": 3,
  "category": "退款政策",
  "version": "v2",
  "department": "客服部"
}
```

其中：

- `source` 表示来源文件；
- `page` 表示原文页码；
- `category` 表示知识分类；
- `version` 表示版本；
- `department` 表示所属部门。
这个主要用于过滤、权限控制、溯源和管理
## 向量数据库的实现原理

### 第一步：写入向量

文档经过 Embedding 模型后得到向量：

```
文本
  ↓
Embedding 模型
  ↓
1024 维向量
```

数据库保存：

```
向量 ID → 原始文本 → 元数据 → 向量
```

---

### 第二步：构建向量索引

如果有 100 万条向量，不建立索引时，查询需要和全部 100 万条向量计算距离。

向量数据库会建立例如：

- HNSW 图索引；
- IVFFLAT 聚类索引；
- IVF-PQ 量化索引。

例如 HNSW 会把相似向量连接成图：

```
       A —— B
      /      \
     C —— D —— E
           \
            F
```

查询时沿图寻找更接近查询向量的节点，而不是扫描全部节点。

---

### 第三步：查询向量进入系统

用户问题：

```
“怎么申请退货？”
```

转成查询向量：

```
q = [0.11, 0.42, -0.32, ...]
```

数据库使用余弦距离、内积或欧氏距离，寻找最接近的向量：

```
查询向量 q
   ↓
ANN 索引
   ↓
候选向量
   ↓
计算距离并排序
   ↓
返回 Top-K
```

返回结果可能是：

```
1. 七天内可以申请退货
2. 申请退货需要订单编号
3. 已使用商品不能退货
```

---

### 第四步：进行元数据过滤

例如只搜索：

```
category = “售后”
tenant_id = “company_a”
version >= “2026”
```

因此真实查询并不只是：

```
找最相似的向量
```

而是：

```
在满足业务条件的向量中，
找最相似的 Top-K。
```

---

## 向量数据库和普通数据库最核心的区别

普通数据库主要擅长：

```
WHERE user_id = 1001
```

或者：

```
WHERE price > 100
```

也就是精确匹配和范围查询。

向量数据库主要擅长：

```
找到与查询向量最相似的 10 个向量
```

它查询的不是“值是否相等”，而是：

> 两个高维向量在语义空间中是否接近。
## 一个完整例子

原始 PDF 中有一段：

```
3.2 退款规则

消费者在签收商品后的七个自然日内，
如果商品未被使用，可以提交退款申请。
```

切成 Chunk 后，数据库可能保存：

```
{
  "id": "chunk_203",
  "text": "消费者在签收商品后的七个自然日内，如果商品未被使用，可以提交退款申请。",
  "metadata": {
    "document_name": "售后服务规则.pdf",
    "section": "3.2 退款规则",
    "page": 8,
    "category": "售后",
    "version": "2026",
    "access_level": "public"
  },
  "vector": [0.18, -0.21, 0.76, ...]
}
```

用户问：

```
没用过的商品签收五天后还能退吗？
```

系统执行：

```
用户问题生成 Query 向量
        ↓
与 vector 比较语义相似度
        ↓
根据 metadata 检查版本和权限
        ↓
取出 text
        ↓
把 text 提供给 LLM
        ↓
LLM 回答：可以，规则允许签收后七个自然日内申请退款
```

所以四个字段各自负责：

```
ID：唯一定位这条记录
原始文本：提供真正的知识内容
元数据：描述、过滤和管理知识
向量：帮助快速找到相关知识
```

你上传的文档也提到，生产级 RAG 经常需要使用元数据完成分类、版本、多租户和权限过滤，再与向量相似度联合查询。
